# Asset-Orchard Verifying Keys

PostFiat pins the verifying keys of its two live Asset-Orchard circuits, swap
and private egress. Validators load them from embedded artifacts instead of
rebuilding them. This page publishes each key's fingerprint, the command that
regenerates the keys from the circuits and compares them, and the latest
result.

The 2026 Orchard soundness advisory
[GHSA-ww9q-8r59-xv46](https://github.com/advisories/GHSA-ww9q-8r59-xv46)
(CVE-2026-54496) is a missing copy constraint in `halo2_gadgets`
variable-base scalar multiplication. It is fixed in `halo2_gadgets 0.5.0` and
`orchard 0.14.0`. The fixed and unfixed circuits share one constraint system
and differ only in the permutation argument, so they have different verifying
keys.

The metadata also carries a `vk_hash`: swap `640e83ff…b828`, private egress

The fingerprint hashes Rust's `Debug` rendering of the key, which a future
compiler could format differently. The script therefore also compares the
regenerated artifact bytes, which do not depend on that formatting.

## Regenerate and compare

From the repository root:

```bash
scripts/verify-orchard-vks          # pins and release keygen, about 6 minutes on 8+ cores
scripts/verify-orchard-vks --quick  # pins only
```

The script:

1. checks that `Cargo.lock` pins `orchard 0.14.0`, `halo2_gadgets 0.5.0` and
   `halo2_proofs 0.3.2`;
2. runs the 14 pin tests:
   `cargo test --locked --release -p postfiat-privacy-orchard --lib vk`;
3. runs the release-only keygen tests
   `swap_full_shape_key_metadata_is_pinned_and_consistent` and
   `private_egress_full_shape_key_metadata_is_pinned_and_consistent`
   (`asset_orchard_circuit_tests.rs:1945`, `:2443`). They rebuild both keys
   from the circuits and assert every metadata field against its pin. The
   `asset-orchard-vk-dev-env` feature lets them write the regenerated
   assemblies, so the script can compare them byte for byte with the committed
   artifacts.

The same keygen tests without the artifact comparison:

```bash
cargo test --locked --release -p postfiat-privacy-orchard --lib \
  full_shape_key_metadata_is_pinned_and_consistent -- --ignored --nocapture
```

## What the result establishes

- **The live keys are the fixed circuits' keys.** Every Asset-Orchard ECC chip
  is built with `CircuitVersion::AnchoredBase`, the fixed scalar
  multiplication (`asset_orchard_circuit.rs:837`, `:1473`, `:1949`;
  `asset_orchard_sinsemilla.rs:674`, `:719`). No code in the repository selects
  `InsecureUnanchoredBase`. The circuits use the affected gadget, `[ivk] g_d`
  (`asset_orchard_circuit.rs:1855`). An unfixed circuit would therefore have
  produced a different key, and the comparison would have failed.
- **Native Orchard actions use the fixed key.** They are verified with
  `orchard::circuit::VerifyingKey::build()` (`verify.rs:1883`). In
  `orchard 0.14.0`, that builds the fixed `FixedPostNu6_2` key. PostFiat pins
  no separate fingerprint for it. No code requests `InsecurePreNu6_2`.

## What it cannot establish

- **Proofs made before public history.** Public git history starts on
  2026-07-17 with commit `11839c14f`. That commit already pins
  `orchard 0.14.0` and `halo2_gadgets 0.5.0`, and already carries today's VK
  pins. Nothing earlier is public. This repository therefore cannot show
  whether any devnet proof created before 2026-07-17 came from a pre-fix
  gadget version or circuit.
- **Where the two replay keys came from.** Their circuit types
  (`asset_orchard_legacy_circuits.rs`) carry only the historical constraint
  system and refuse synthesis, so keygen cannot regenerate them.
  Reconstruction checks their fingerprints against their pins. But the fixed
  and unfixed circuits share one constraint system, so reconstruction cannot
  show which version produced the replay assemblies. The commit they were cut
  from, `3218ec53`, is not in public history.
- **Native Orchard proofs from older versions.** An Orchard action proof made
  with `orchard` below 0.14.0 would not verify under the fixed key. Public
  history cannot show whether any such proof exists in the pre-publication
  devnet.

Any change to a circuit, its dependencies, or a pinned key needs new
compatibility vectors and cryptographic review. Updating a recorded
fingerprint is not, by itself, a review.
